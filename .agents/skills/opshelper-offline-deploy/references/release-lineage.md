# 基于上次 release 的连续升级

## 选择基线：目录是证据，现场版本是适用条件

先列出本项目 `releases/`，读取用户指定的上次发布目录。未指定时，从发布清单、交付记录及用户上下文确定最近一次已交付版本；目录名排序只能帮助找候选，不等于已部署。候选目录只用于寻找证据，不能硬编码为固定的前序版本。

区分三个版本：上次已交付版本、本次源代码版本、现场正在运行的版本。可访问现场时核对实际镜像 ID/配置与迁移状态；不能访问时可先针对已交付版本生成有明确适用条件的升级方案，在执行前要求现场核对。不要把“现场未核实”写成“已核实”，也不因它阻止独立打包工作。

多个现场处于不同版本时，为每个被支持的来源列出直升或中间版本步骤。不能把 `A → B` 验证自动推广成 `A → C` 或 `B → C`；无法证明跳版安全时，准备连续中间包或明确不支持该来源。

## 读取旧目录的实际内容

优先读取并校验旧 release 中实际存在的证据：

- 最终归档和外部 `.sha256`；
- `UPGRADE.md`、发布记录，以及 `release-manifest.json`、源码/镜像清单、发布 Compose、配置模板或验证文档（如果历史 release 包含）；
- 数据库迁移、配置补丁或其他非镜像升级资产（如果有）。

旧包可能没有新清单格式，不要求用户重打历史包。记录可得到的证据和缺口，不能伪造补全。历史归档保持不变，本次分析写到本次 release。

核对旧包的实际目录结构：配置和清单可能在归档旁边，`images.tar.gz` 也可能在最终压缩包内部；`package-contents.sha256` 描述的是包内文件，不可在外层目录直接当完整部署校验执行。需要展开时在独立 `.temp/` 目录解压，核对路径，避免覆盖旧发布物或现场配置。

`source-manifest.json` 中的 Git HEAD 可能伴随未提交改动，所以 HEAD 不一定代表完整已交付源码。先看其工作区说明和逐文件哈希；只有哈希匹配才能把某提交的文件认定为旧包实际内容。需要旧迁移 SQL 或代码时，可从匹配的 Git 历史、保留快照或旧 API 镜像只读提取，不启动旧应用、不连接生产数据库。缺少旧 SQL 内容时不能凭迁移名字宣称兼容。

## 生成逐项版本差异

以实际旧发布内容对比本次快照，把下列差异集中写入 `UPGRADE.md`；默认不再单独生成 `RELEASE-DIFF.md`：

| 范围 | 必须确认的差异与影响 |
| --- | --- |
| 六类镜像 | 旧/新 tag 与 config hash 或 image ID；哪些变化、哪些复用；runtime 是否重建 |
| Prisma | 旧已包含/现场已应用/本次新增的迁移清单及顺序；旧迁移是否被修改；数据转换和锁表影响 |
| 数据库引擎 | PostgreSQL 主版本变化及是否超出本次原地升级流程 |
| 配置 | Compose、nginx、环境变量新增/删除/默认值变化；现场值如何保留与合并 |
| 持久化 | 数据目录、挂载、权限、UID/GID、runtime 状态格式兼容性 |
| 业务行为 | 对话、文件、权限、计划、模型/provider/技能依赖的变化和针对性验收 |

没有变化也明确写出依据。源码清理、文档改动可以不产生数据库迁移，不编造“升级必有迁移”。镜像 tag 改变也不能单独证明内容变化。

## 输出本次可执行升级方案

`UPGRADE.md` 顶部写明：支持来源 release ID、目标 release ID、旧归档校验标识、现场版本核对方法、能否直升及证据。如果需要中间版本，逐段给出 `A → B → C` 和每段包、迁移、停点及回退基线，不能只画箭头。

按 upgrade.md 的备份/迁移约束生成具体命令，使用实际包名与版本标签；不要留下让用户自行猜测的 `<old-tag>`、`<new-tag>`。现场路径/端口未知时明确列为待填写参数，不伪造现场值。说明：

1. 本次加载哪些镜像，是否复用旧基础镜像；
2. 现场哪些文件替换，`.env` 哪些键保留/新增/改变；
3. 本次迁移确切清单、执行顺序和失败停点；
4. 哪些平台/用户容器需要重建，如何保留数据；
5. 本次变化对应的验收项；
6. 退回哪一个 release，是否必须恢复数据库和文件备份，以及新写入损失边界。

升级包只包含相对基线有改动的镜像，不提供全量镜像包；全新部署才交付完整集合。`UPGRADE.md` 区分本次携带镜像与现场必须已有的基线镜像，每项记录准确 tag、架构和 config hash/image ID。未变镜像保留原标签；同一镜像被 api/migrate 等多个服务复用时只导出一次。

按实际构建依赖判断影响：Dockerfile、锁文件、共享代码或构建参数变化可能影响多个镜像，不能只按 apps 子目录是否改动判断。先分析受影响镜像，必要时构建核对；已明确复用的基础镜像不要为了生成发布而拉取浮动标签引入无关更新。缺乏基线证据时不得把镜像擅自列为“未变”，先补齐证据再确定集合。

部署前必须检查 `UPGRADE.md` 声明的基线镜像；缺失或身份不符时，在任何停机/迁移之前停止升级执行，从相应历史 release 取得准确镜像或提供独立的缺失镜像补包，不在线 pull，也不因此默认改成交付全量升级包。若历史 release 本身是增量包，沿发布链追溯到实际包含该镜像的归档，并在文档列出来源文件及校验值。

只有数据库、配置或其他非镜像内容变化而无镜像变化时，交付这些实际变化和 `UPGRADE.md`，省略 `images.tar.gz` 及 `docker load` 步骤，不制造空镜像归档。升级验证应证明“`UPGRADE.md` 声明的基线 + 本次最小包”足够运行，不能借用构建机未声明的缓存镜像而误判成功。

## 为下一次升级留下基线

不再为了内部追踪强制增加 `release-manifest.json` 等交付文件。把下一次升级真正需要的血缘信息集中保留在 `UPGRADE.md`：release ID 与时间、前序 release 及归档校验值、支持来源和是否直升、源码提交与工作区状态、包含镜像和基线镜像的准确身份、完整迁移 ID/哈希、配置变化、数据库/runtime 版本以及验证层级。不得记录密码。

release 目录默认只保留最终升级归档、外部 `.sha256` 和便于直接阅读的 `UPGRADE.md`；归档内部只放最小升级资产、`UPGRADE.md` 与 `SHA256SUMS`。用户明确要求额外审计清单时再生成，不作为普通升级的默认交付。

连续升级演练要来自受支持旧版本的隔离实例/授权数据副本，验证旧数据经过新增迁移仍可使用，并演练与升级路径对应的恢复。没有执行时写“待演练”，不能因已生成文档或全新安装通过就标记升级验证成功。
