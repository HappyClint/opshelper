# 已有离线实例升级与回退

先按 [release-lineage.md](release-lineage.md) 读取上次 release 文件夹并固定 `from → to`。下面是执行约束；实际交付必须将其落实为本次版本的具体方案，不能原样复制通用流程。

## 先确定可升级范围

现场“新版本已经运行”不说明它与任意新包兼容。读取旧发布清单、实际运行镜像、Compose、数据目录、PostgreSQL 版本和已应用迁移；对比新版本源码及迁移 SQL。记录项目名、部署路径、data 路径、UID/GID、端口、数据库版本、runtime 版本及动态用户容器的实际挂载。不要在报告里输出密码。

确认新版本迁移链是旧版本的连续后继；不能修改已经应用的迁移文件，不能拿 `prisma db push` 代替升级。特别检查非空列、唯一约束、删除列/表、数据转换、长时间锁表以及旧代码对新 schema 的兼容性。没有对实际旧 schema 验证过时，将升级列为待验证，不能仅凭 migrate deploy 在空库成功就放行。

本流程默认同一 PostgreSQL 主版本、相同架构与 UID/GID、原地替换应用。跨 PostgreSQL 主版本需单独的 pg_upgrade 或逻辑迁移方案；不得把旧 postgres 数据目录直接交给新主版本。跨机器/路径恢复还要处理数据挂载、容器 ID 与 lease 等记录以及同 daemon 的用户容器重名问题，依据当前恢复实现验证，不套用下面的原地升级。

在隔离副本演练前隔断真实模型/工具/MCP 访问和定时任务外部副作用；生产数据副本仍是敏感数据。旧版缺少完整发布清单、备份或迁移兼容证据时，先完成可独立推进的包制作与文档，再取得缺失信息。

## 升级前可以不停机完成的准备

1. 解压最小升级包到独立 staging 目录并校验，不覆盖现用 `.env`、Compose 和配置。
2. 按 `UPGRADE.md` 核对基线镜像标签和身份，缺失时先从指定历史归档恢复；再 `docker load -i images.tar.gz` 加载本次有改动的镜像。未变镜像保持基线引用，保留旧镜像并记录新旧标签与 image ID。若本次无镜像变化，跳过加载。
3. 若包内没有配置资产，继续原样使用现场 `.env`、Compose 和 nginx 配置。只有本次确有配置变化时才合并包内文件或补丁，保留原数据库密码、项目名、数据路径、UID/GID、端口、模型和用户配置；不得用初始化模板覆盖现场 `.env` 或重新生成管理员密码。
4. 仅在包含配置变化时校验合并后的 Compose、bind 路径及 nginx 相对路径；不能在 staging 验证后移动文件导致挂载含义变化。
5. 把实际命令、维护窗口、受影响实例、备份位置、迁移范围和回退路径写入 `UPGRADE.md`。若用户只授权准备，完成这些工作后再请求实际停机授权；已经授权升级则继续。

## 停写和一致性备份

目标离线包没有 `scripts/opshelper.py`，默认给出手工命令。若现场明确有匹配版本的备份工具且允许使用，可按其文档操作，但不要假设所有目标机都装有 Python 或该脚本。

推荐手工路径为完整冷备份，实际顺序如下：

1. 让用户完成/取消活动执行，处理等待回答、排队和待恢复状态，暂停新增任务；从管理界面或按当前 schema 校验队列，不能只看容器状态。核实本次停写期间任务的迟到/跳过规则。
2. 使用原配置停止 `nginx web worker api`。重新检查数据库里是否仍有阻碍备份的执行状态；有则先恢复原版本处理后重试，不假定停止进程等于任务已结束。
3. 根据 `DATA_ROOT_HOST/users/` 实际 bind 精确列出本实例动态用户容器，停止这些容器。`docker-compose stop` 不会停止它们，不能按所有 `opshelper-user-*` 批量停其他实例。
4. 在 PostgreSQL 仍运行且业务全部停写时可另做逻辑转储：

   ```bash
   docker-compose --env-file .env exec -T postgres pg_dump -U opshelper -d opshelper -Fc --no-owner --no-acl > <backup-dir>/database.dump
   ```

   用户名/库名按现场值替换。检查命令退出码和归档可读性；仅文件非空不证明可恢复。
5. 正常停止 PostgreSQL，确认没有剩余容器写入该 data。将完整 data 冷备份到 data 之外的新目录，同时保存旧 `.env`、Compose、nginx 配置、新旧镜像清单和旧发布包。保留数值 UID/GID、权限、隐藏文件；存在外部表空间、额外挂载或指向外部的符号链接时，单独纳入一致性备份，不能把普通 tar 当完整备份。
6. 对 Linux GNU tar 的普通本地 data 布局，可生成如下模式的命令，必须替换成已核实的绝对路径并检查目标不在源 data 内：

   ```bash
   tar --numeric-owner --acls --xattrs -czpf <backup-dir>/data-cold.tar.gz -C <data-dir> .
   ```

   若文件系统/工具不同，调整保留属性的方法。备份目录 700、含密文件 600，生成校验清单并校验 tar/gzip 完整性。不要 `source .env` 来取路径，把 dotenv 当 shell 执行。

只复制 workspace 或只备份数据库不能恢复完整应用；运行中的 postgres 数据目录 tar 也不是本流程认可的一致性备份。打包端升级承诺需要有恢复演练证据；实际升级前要核实现场备份完整性、空间和旧镜像仍可用。

## 部署新版本与迁移

备份完成后，只应用包内实际提供的非镜像变更；没有配置文件或补丁时，不替换现场 Compose、nginx 或 `.env`。始终使用原项目名与 data 路径，不执行 init、不创建空库、不覆盖用户/模型配置。

建议把“迁移成功”和“启动应用”分开形成故障停点：

1. 使用新部署配置启动 postgres，禁止构建/拉取，等待健康。保持相同 PostgreSQL 主版本。
2. 使用新 API 镜像执行一次临时迁移服务：

   ```bash
   docker-compose --env-file .env run --rm --no-deps migrate
   ```

   依赖发布服务的 `pull_policy: never`；执行前已检查镜像都存在。当前 migrate 只执行数据库迁移；升级或恢复禁止执行 bootstrap 或 seed。旧发布包若仍将 seed 绑定到迁移，需使用与该版本相符且仅执行迁移的命令。记录迁移退出码与 Prisma 状态，退出非 0 则保持新应用停止；不要自动循环重试、改 migration 表或用 `migrate resolve` 掩盖失败。
3. 迁移成功后启动平台。若用普通 `up -d --no-build --pull never`，先确认 Compose 只执行 migrate、不执行 seed；不能以旧 migrate 容器曾退出 0 作为新迁移已执行的证据。需要避免重复迁移时，分步使用 `up -d --no-deps --no-build --pull never api`，验证 API 健康后启动 worker/web，最后验证 Web 健康并启动 nginx。
4. runtime 镜像更新须检查当前 `container-service` 的镜像漂移重建行为。已停止用户容器不会因为 `docker load` 自动换镜像。若需显式移除容器以重建，只删除已核实归属于本 data 的已停止容器对象，保留 bind 数据，并验证当前代码能处理旧 Docker ID；不可清除整个用户 state。
5. 核对五类平台服务健康、管理员及普通用户登录、已有会话与历史文件、用户权限和智能体分配、真实问答/协作、文件写入及定时任务。使用实际物理机入口做 LAN 验证，记录实际运行 image ID，别只看标签。

## 失败与回退

迁移失败或新版本业务验收失败后，停止新应用及属于该实例的用户容器；保留失败日志和现场。是否允许继续排错或回退由已有授权决定，不继续对生产数据库试错。

- 只有在确认 schema 未改变，或旧代码已验证兼容新 schema 时，才可仅换回旧应用/runtime 镜像。
- schema 已变更且兼容性未证实时，回退使用同一停写时点的数据备份与旧发布配置/镜像：停止 PostgreSQL，把失败 data 保留到独立位置，恢复到空目标；不要把旧 tar 叠加解压到新数据库目录。
- 冷备份恢复使用旧 PostgreSQL 主版本和数值 UID/GID，恢复旧 `.env` 与挂载路径。新版本曾重建的用户容器需精确停止并按当前恢复逻辑处理旧 ID/挂载，避免以新 runtime 运行旧配置。
- 若用逻辑转储恢复，必须恢复到空数据库，并配套恢复同一时间点 agents/config/users 数据；参考当前工具的容器状态/lease 清理逻辑，禁止凭猜测修改状态字段。
- 原地恢复旧路径可避免跨路径挂载变化；换目录恢复前必须解决已有用户容器名冲突，防止源和恢复实例同时运行任务。
- 告知用户回退会丢失备份时点之后的新写入。若升级后已开放业务，不能声称恢复旧备份“无损”；先保留新增数据并具体评估。

成功后保留旧包、旧镜像和备份，直到用户认可现场业务验收并明确允许清理。只处理本次测试资源，不顺手做全局镜像清理或历史重写。
